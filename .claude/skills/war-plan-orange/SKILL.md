# War plan orange: second K2-18 b grid sweep (narrowed parameter space)

## Why this sweep exists

The original 1024-point grid sweep (`grid_sweep_configs/full_parameter_sweep.toml`,
see CLAUDE.md) covered too broad a parameter space: of 700+ successfully-completed
cases, only ~26 achieved `chisq_madhu_2023_reduced < 2` against the Madhusudhan
2023 spectrum. This second sweep narrows the ranges toward the region that
produced most of those good fits:

| Axis | Orange sweep values | Original sweep values |
|---|---|---|
| `H_budget` (ppmw) | 30000, 40000, 50000, 60000 | ~10000–50000 (logspace) |
| `C_budget` | 5e-4, 5e-3, 5e-2, 5e-1 | 3.2e-3–3.2 |
| `N_budget` | 5e-4, 5e-3, 5e-2, 5e-1 | 9e-4–0.9 |
| `S_budget` | 5e-4, 5e-3, 5e-2, 5e-1 | 4e-3–4.0 |
| `fO2_shift_IW` | -4, -3, -2, -1 | -3, -2, -1, 0 |

Same fiducial config (`k218b_fiducial.toml`), same module selection — only
the swept axes differ. Still a 4×4×4×4×4 = 1024-point full factorial grid,
so it reuses the original's 16-batches-of-64 split scheme exactly (see
"Batch layout" below).

## Namespacing — orange never touches the original sweep's files

Every orange-specific path is generated by `scripts/generate_grid_configs.py`
(a new, reusable generator — see its docstring for the axis-value/split-rule
inputs and its own partition self-check) and kept fully separate from the
original sweep to avoid `GRID_INDEX_LEGEND.txt`/`grid_master.csv`
cross-contamination (index `H0` means a different physical value in each
sweep):

| | Original sweep | Orange sweep |
|---|---|---|
| Full-sweep reference | `grid_sweep_configs/full_parameter_sweep.toml` | `grid_sweep_configs/orange_full_parameter_sweep.toml` |
| Batch configs | `grid_sweep_configs/batch_configs/batchNN.toml` | `grid_sweep_configs/orange_batch_configs/batch_orangeNN.toml` |
| PROTEUS output | `k218b_project_main_parameter_sweep_batchNN/` | `k218b_project_orange_sweep_batch_orangeNN/` |
| Harvested cases | `simulation_data/` (flat) | `simulation_data/orange_sweep/` (flat) |
| Summary CSV | `simulation_data/grid_master.csv` | `simulation_data/orange_sweep/grid_master_orange.csv` |
| Cron harvest | `0 7 * * *`, no flags (uses defaults) | `5 7 * * *`, orange overrides (see below) |
| Cron log dir | `logs/` | `logs/orange/` |

Batch filenames start with the literal string `batch` (not `orange_batch`)
because `harvest_completed_cases.py`'s `discover_batches()` and
`generate_gapfill_configs.py` both glob strictly for `batch*.toml` —
`batch_orangeNN.toml` satisfies that while staying visually distinct from
the original `batchNN.toml`.

Every command below that touches orange data passes explicit
`--full-sweep`/`--batch-configs`/`--dest` flags pointing at these paths —
**never rely on the scripts' bare defaults**, which point at the original
sweep. No script itself needed modifying; `harvest_completed_cases.py`,
`generate_grid_status.py`, `generate_gapfill_configs.py`,
`build_grid_summary.py`, and `compute_spectral_chisq.py` all already accept
these overrides.

## Batch layout

Split by `fO2_shift_IW` (one value/batch-group) × `H_budget` low/high half ×
`C_budget` low/high half; `N_budget`/`S_budget` stay the full 4-value axis
in every batch. `batch_number = f*4 + hh*2 + ch + 1` (same numbering formula
as the original sweep). `batch_orange01` (fO2=-4, H=[30000,40000],
C=[5e-4,5e-3]) — the most-reducing, lowest-volatile-budget corner, and
therefore the combination most likely to expose any solver instability at
the new parameter boundaries — was already launched as a pilot on
**cap001c** on 2026-08-06 ahead of the Monday launch, specifically to
smoke-test the new parameter ranges before committing the whole cluster to
them. Confirmed running for real (queued→running progression, not an
instant dry-run-like finish).

## Background/unattended execution — what actually runs without you

This Claude Code session runs on a persistent host (not the laptop), so the
daily cron jobs and any detached `tmux` session on a cluster machine already
survive regardless of whether the laptop is open — proven over several
weeks by the original sweep's own cron-driven harvesting.

**A scheduled cloud routine (`schedule` skill / `RemoteTrigger`) was
investigated and ruled out for mid-week monitoring**: routines execute as
fully isolated cloud sessions with only a git checkout of a specified
GitHub repo — per the `schedule` skill's own documentation, they "cannot
access local files, local services, or local environment variables." That
means a routine can never SSH into the private IoA cluster or read the
NFS-mounted `/data/rdc49-2` project data (most of which is gitignored
anyway). **Do not attempt to set one up for this** — it cannot work, and
this was confirmed directly from the skill's setup notes, not just
guessed.

So the only automation actually running during the week is:
1. Detached `tmux` sessions on each cluster machine (survive independent of
   this session).
2. The daily cron harvest (`5 7 * * *`, orange overrides, logs to
   `logs/orange/harvest_YYYY-MM-DD.log`) sweeping finished cases into
   `simulation_data/orange_sweep/`.

There is **no automated judgment layer** mid-week — nothing will notice a
stuck batch, a systematic crash pattern, or (if the sweep runs past one
week) the next Monday's cluster reboot on its own. That's why the Monday
launch below does all of the judgment-requiring work up front, and why
"On return" below expects to do any needed recovery then, not assume it
already happened.

## Monday launch

1. **Re-diff the fiducial config** (mandatory every time, per the
   `launch-grid-batch` skill):
   ```bash
   diff /data/rdc49-2/K218b_project/k218b_fiducial.toml /data/rdc49-2/PROTEUS/input/nogit_k218b_project/k218b_fiducial.toml
   ```
   Fix drift (copy the project's version over) before launching anything.
2. **Check `batch_orange01`'s status** — don't touch it:
   ```bash
   python3 scripts/harvest_completed_cases.py --full-sweep grid_sweep_configs/orange_full_parameter_sweep.toml --batch-configs grid_sweep_configs/orange_batch_configs --dest simulation_data/orange_sweep --summary-only
   ```
   Whatever state it's in (still running / fully harvested / partway
   harvested), leave it alone — `proteus grid` destructively `rmtree`s an
   existing non-empty output directory, so re-launching it would wipe
   in-progress or completed work.
3. **Live machine-load survey** across all 14 known machines (same
   procedure as `grid_sweep_cluster_howto.md` "Choosing a machine" — this
   table goes stale immediately, always re-check):
   ```bash
   for h in cap001a cap001b cap001c cap001d cap002b cap002c cap002d cap003a cap003b cap003c cap003d cap004a cap004d cap005a; do
     echo "== $h =="
     ssh -o ConnectTimeout=6 $h "uptime; ps aux --sort=-%cpu | grep -Ei 'python|julia|proteus|agni|spider' | grep -v grep | head -5"
   done
   ```
   `cap001c` is already running the orange pilot — skip it. Watch for
   other users' real simulation processes (as of 2026-08-06, `cap003b` was
   busy with another user's `Prospector` MCMC job at load ~12 — re-check,
   don't assume it's still busy).
4. **Assign `batch_orange02`..`batch_orange16` (15 batches)** to idle
   machines from the survey — one per machine, doubling up on `cap005a`
   (112 cores) in two concurrent tmux sessions if it's free, same
   trade-off as the original sweep's launch. If fewer than 15 machines are
   free, leave the excess unassigned rather than launching into a busy
   machine — catch up on it later in the week or note it for next Monday.
5. **Launch** via `scripts/launch_batches.sh` with a manifest built from
   the live survey (row format: `machine,config_path,session_name`):
   ```bash
   cat > /tmp/orange_manifest.csv <<'EOF'
   # machine,config_path,session_name
   <machine1>,grid_sweep_configs/orange_batch_configs/batch_orange02.toml,proteus_batch_orange02
   <machine2>,grid_sweep_configs/orange_batch_configs/batch_orange03.toml,proteus_batch_orange03
   ...
   EOF
   scripts/launch_batches.sh /tmp/orange_manifest.csv
   ```
   (Or launch each manually per `grid_sweep_cluster_howto.md` "Steps to
   launch a sweep" if preferred — same detached-tmux
   `nice -n 19 proteus grid -c <config>` sequence either way.)
6. **Confirm** each launch shows real `queued → running → exited`
   progression (via `tmux capture-pane`/`manager.log`), not an
   instant-finish dry-run-like pattern.
7. **Record the actual assignment** in "Currently running orange sweeps"
   below before ending the session.

## Weekly-reboot risk

The IoA cluster reboots most Mondays around 05:45–05:55, killing every
running process cluster-wide. Since this sweep launches Monday morning
(after that day's reboot has already happened), the immediate launch isn't
at risk — but if the sweep is still running past **the following** Monday,
those remaining cases get killed mid-run with no automated recovery (see
above). Recovery:

```bash
python3 scripts/generate_gapfill_configs.py --full-sweep grid_sweep_configs/orange_full_parameter_sweep.toml --batch-configs grid_sweep_configs/orange_batch_configs --dest simulation_data/orange_sweep --output-dir grid_sweep_configs/orange_gapfill_configs/$(date +%Y%m%d_%H%M%S)
# then launch the generated launch.sh on a free machine, and check on it with:
python3 scripts/harvest_completed_cases.py --full-sweep grid_sweep_configs/orange_full_parameter_sweep.toml --batch-configs <that gapfill dir> --dest simulation_data/orange_sweep --summary-only
```

## On return / wrap-up

1. Final harvest pass (drop `--summary-only`) to drain any last completed
   cases:
   ```bash
   python3 scripts/harvest_completed_cases.py --full-sweep grid_sweep_configs/orange_full_parameter_sweep.toml --batch-configs grid_sweep_configs/orange_batch_configs --dest simulation_data/orange_sweep
   ```
2. Check for stragglers (still running / killed / crashed) and gap-fill
   per the "Weekly-reboot risk" recipe above if needed.
3. Rebuild the summary CSV **with** the chi-squared columns in one step
   (never run `build_grid_summary.py` alone afterward — same
   wipes-the-chisq-columns gotcha as the original `grid_master.csv`, see
   the `grid-summary-and-chisq` skill):
   ```bash
   python3 scripts/compute_spectral_chisq.py --full-sweep grid_sweep_configs/orange_full_parameter_sweep.toml --dest simulation_data/orange_sweep --output simulation_data/orange_sweep/grid_master_orange.csv
   ```
4. Review the `chisq_madhu_2023_reduced` (and the other 3 chisq) column
   distribution against the original sweep's ~26/759 hit rate to see
   whether narrowing the range worked as intended.
5. Note: `simulation_data/orange_sweep/GRID_INDEX_LEGEND.txt`'s
   auto-generated header text says it was "Regenerated automatically... from
   grid_sweep_configs/full_parameter_sweep.toml" — that's a hardcoded
   string in `harvest_completed_cases.py`'s own template, not a bug
   specific to orange; the actual axis values below that line are correct
   for whichever `--full-sweep` was actually passed (verified against
   `orange_full_parameter_sweep.toml`'s values on 2026-08-06). Not worth
   patching the shared script for a cosmetic string.
