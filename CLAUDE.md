# K2-18 b Molten Gas Dwarf Project

## Goal

Test the **molten gas dwarf hypothesis** for the sub-Neptune K2-18 b using the
`PROTEUS` coupled interior-atmosphere evolution model. The plan:

1. Run PROTEUS with fiducial parameters appropriate for the K2-18 b system
   (planet mass/radius, instellation, host star spectrum, etc.), sweeping a grid
   over:
   - mantle oxygen fugacity (fO2)
   - bulk volatile **hydrogen** budget
   - bulk volatile **carbon** budget
   - bulk volatile **nitrogen** budget
   - bulk volatile **sulphur** budget
2. Atmospheric chemistry and the synthetic transmission spectrum for each
   grid point are generated automatically as part of the PROTEUS pipeline
   itself (not a separate post-processing step) and land in that run's own
   output subdirectory.
3. Compare synthetic spectra against one or more observed K2-18 b transmission
   spectra.
4. Assess whether the observations are consistent with K2-18 b being a molten
   gas dwarf (permanent magma ocean + H2-dominated envelope), or whether they
   rule it out.

This project is the natural follow-up to the predecessor population-level
study in `reference_papers/calder_2026.pdf` (source in `paper/`), which
established the "solidification shoreline" concept and explicitly flagged that
an evolutionary, self-consistent comparison of K2-18 b against its observed
spectrum (rather than mass/radius/instellation alone) was the needed next
step — that is this project.

## Skills

Detailed, task-specific procedures that used to live in this file have been
split out into `.claude/skills/` (loaded on demand, not on every
conversation — see "Working conventions" below). Quick map:

- `launch-grid-batch` — launching a `proteus grid` batch or single run:
  fiducial-config drift check, `nice`, batch sizing, the `raw_grid_output/`
  symlink bug.
- `move-completed-sweep` — moving a *fully finished* sweep into
  `simulation_data/` (`scripts/move_sweep.py`).
- `harvest-batches` — monitoring/harvesting *partially finished* sweeps
  (`scripts/harvest_completed_cases.py`), outcome categories, the daily
  cron job.
- `war-plan-orange` — launching/monitoring/harvesting the second,
  narrowed-parameter-space grid sweep (the "orange" sweep, `orange_*`
  configs and `simulation_data/orange_sweep/` — fully separate namespace
  from the original sweep above, generated by
  `scripts/generate_grid_configs.py`).
- `recover-interrupted-grid-points` — regenerating configs for cases killed
  mid-run, e.g. by the weekly cluster reset (`scripts/generate_gapfill_configs.py`).
- `recover-vulcan-crashes` — re-running VULCAN + petitRADTRANS
  post-processing in place for category-7 cases (main loop succeeded, only
  the offline VULCAN step crashed), across the cluster
  (`scripts/generate_vulcan_rerun_configs.py`, `scripts/launch_vulcan_reruns.sh`,
  `scripts/resume_vulcan_rerun.sh`, `scripts/retag_vulcan_reruns.py`).
- `cluster-tmp-cleanup` — clearing leaked `/tmp/proteus_*` scratch dirs on
  the cluster machines (`scripts/cleanup_proteus_tmp.py`), the daily cron job.
- `grid-summary-and-chisq` — rebuilding `simulation_data/grid_master.csv`
  and its `chisq_*` columns (`scripts/build_grid_summary.py` /
  `scripts/compute_spectral_chisq.py`), including the run-order gotcha.
- `proteus-config-review` — checklist for writing/reviewing any PROTEUS
  TOML config in this project.
- `compile-paper` — compiling `paper/main.tex`.
- `backup-after-push` — mirroring the project to the external hard drive;
  **required after every `git push`**, see "Working conventions" below.

## Directory layout

- `raw_grid_output/` — staging area that batch grid configs' `symlink`
  field points PROTEUS at directly, so sweep output is written here (on
  this project's own disk) rather than under PROTEUS's own `output/`
  directory. Currently disabled by an upstream PROTEUS bug — see the
  `launch-grid-batch` skill for the current fallback layout and how to
  re-enable it. Not yet reviewed/checked — treat anything here as
  untrustworthy until moved into `simulation_data/`.
- `simulation_data/` — raw output from PROTEUS grid-sweep runs (fO2 x H x C x
  N x S), one subdirectory per sweep (each containing one `case_NNNNNN/`
  subdirectory per grid point), following the PROTEUS `output/<run>/` layout.
  PROTEUS itself never writes here directly: completed sweeps/cases are only
  moved here by hand or by script (see the `move-completed-sweep` and
  `harvest-batches` skills) after being checked over. So absence of a run
  here doesn't mean it hasn't finished — it may just not have been
  reviewed/moved yet. Treat this as **read-only input** to plotting
  scripts — never hand-edit simulation output.
- `plotting_scripts/` — Python scripts that read from `simulation_data/` and
  produce figures. Currently empty. Each script's output figures should be
  written into a subdirectory of `paper/Figures/`.
- `scripts/` — project-management utility scripts (not paper-figure
  scripts; those go in `plotting_scripts/`):
  - `move_sweep.py` — moves one whole, fully-finished sweep into
    `simulation_data/`. See the `move-completed-sweep` skill.
  - `harvest_completed_cases.py` — incrementally harvests finished cases
    out of still-running batches. See the `harvest-batches` skill.
  - `generate_gapfill_configs.py` — regenerates single-point launch
    configs for grid points killed mid-run. See the
    `recover-interrupted-grid-points` skill.
  - `analyze_grid_sweep.py` — a separate, pre-existing, more thorough
    per-sweep analysis tool, not written by this assistant, whose
    log-cross-checking approach `harvest_completed_cases.py`
    reuses/adapts — see its own docstring for the single-sweep-focused
    analysis and plot-collection features it has that
    `harvest_completed_cases.py` doesn't.
  - `launch_batches.sh` — bash script that automates launching a manifest
    of batches across cluster machines. See the `launch-grid-batch` skill.
  - `generate_grid_configs.py` — generates a full-sweep reference TOML plus
    its 16 batch-split configs from a set of axis values, with a
    partition-correctness self-check (zero overlap, full coverage) before
    writing anything. Used to produce the `orange_*` sweep configs; see the
    `war-plan-orange` skill.
  - `build_grid_summary.py` / `compute_spectral_chisq.py` — rebuild
    `simulation_data/grid_master.csv` and its `chisq_*` spectral-fit
    columns. See the `grid-summary-and-chisq` skill for the run-order

  - `reclassify_vulcan_crashes.py` — a one-time migration script, run

    mis-tagged `2_fatal_crash_main_loop` to the new

  - `cleanup_proteus_tmp.py` — deletes orphaned `/tmp/proteus_*` scratch
    directories from the 14 cluster machines over SSH. See the
    `cluster-tmp-cleanup` skill.
  - `generate_vulcan_rerun_configs.py` / `launch_vulcan_reruns.sh` /
    `resume_vulcan_rerun.sh` / `retag_vulcan_reruns.py` — re-run VULCAN +
    petitRADTRANS post-processing in place for category-7 cases (main loop
    already succeeded, only the offline VULCAN step crashed), across the
    cluster. See the `recover-vulcan-crashes` skill.

  predecessor paper above).

  compute the `chisq_*` columns in `simulation_data/grid_master.csv` (see
  the `grid-summary-and-chisq` skill). One subdirectory per source:
  - `madhusudhan_2023/` — Madhusudhan et al. 2023 (ApJL). JWST NIRISS SOSS
    and NIRSpec G395H, each as `_native` (full resolution, used for the
    chi-squared fit) and `_lowres` (plotting only, per that folder's own
    `Readme.txt`/this project's README.txt).
  - `madhusudhan_2025/` — Madhusudhan et al. 2025 (ApJL). JWST MIRI LRS,
    reduced independently by two pipelines, JExoRES and JexoPipe
    (`_jexores`/`_jexopipe` files) — genuinely alternative reductions of
    the *same* wavelength range, not complementary coverage.
  - `hu_2026/` — Hu et al. (bib key `Hu2025` in `paper/references.bib` as
    of this writing; confirm whether "hu_2026"/`Hu2025` refer to the same
    paper before assuming a `Hu2026` bib key exists). Four subfolders with
    heavy redundancy across different pipelines/visits/detectors —
    `niriss_nameless/` (2 files, NIRISS SOSS order1+order2 — same
    exposure, two diffraction orders, NOT independent), `nirspec_combined/`

    the 4 `*_shifted.dat` files are alternate reductions of the same
    data), `nirspec_eureka_by_visit/` and `nirspec_exotedrf_by_visit/`

    `compute_spectral_chisq.py` at all).
  See `scripts/compute_spectral_chisq.py`'s own docstring for exactly
  which files it uses per source and why (overlap trims between
  same-instrument/same-exposure reductions, kept-as-is for genuinely
  different instruments).
- `k218b_fiducial.toml` — the fiducial PROTEUS configuration for this
  project: every non-default parameter is set explicitly with an inline
  comment justifying the choice. This is the base config that the grid sweep
  is built from — each grid point's config should equal this file with only

## PROTEUS essentials for this project

PROTEUS is a coupled atmosphere-interior evolution framework built from
swappable modules per physics domain (interior structure, interior
energetics, outgassing, climate, escape, observation, atmospheric
chemistry). `SPIDER`/`ARAGOG` + `CALLIOPE` is the generic/default module
combination described in `proteus_CLAUDE.md`, but **this project uses a
different combination** — see "Fiducial configuration" below for the exact
modules `k218b_fiducial.toml` selects. A run starts fully molten and
integrates forward until either the mantle solidifies or the planet reaches
global energetic steady state (instellation = internal heat + thermal
emission) — the latter is the "permanent magma ocean" outcome this project
is testing for K2-18 b.

Relevant CLI entry points (see `proteus_CLAUDE.md` for full detail):

- `proteus start -c <config.toml>` — run a single simulation.
- `proteus grid` — run a parameter grid/sweep. This is what generates the
  sweep folders that get moved into `simulation_data/` for the fO2 x H x C
  x N x S sweep. See the `launch-grid-batch` skill before launching one —
  in particular, always run it niced (`nice -n 19 proteus grid -c
  <config>`), never bare.
- `proteus plot -c <config.toml> all` — PROTEUS's own built-in diagnostic
  plots (distinct from the custom `plotting_scripts/` figures for the paper).
- `proteus doctor` — environment diagnostics if a run environment looks broken.

Configuration is via TOML. Every config must set an explicit
`planet.elements.O_mode` (`"ic_chemistry"`, `"ppmw"`, `"kg"`, or
`"FeO_mantle_wt_pct"`) governing how oxygen is accounted for relative to the
mantle fO2 buffer — this directly interacts with the fO2 sweep axis of this
project, so pick the mode deliberately and keep it consistent across the grid
so that fO2 comparisons are apples-to-apples. The H/C/N/S volatile budgets for
the sweep are set the same way (`ppmw`/`kg` per element). See the
`proteus-config-review` skill for a fuller checklist of PROTEUS config
gotchas before writing or reviewing any TOML here.

### Fiducial configuration: `k218b_fiducial.toml`

This is the authoritative base config for the project (project root). Every
grid-sweep config should derive from it, overriding only the swept
parameters. Key points:

- **Module selection** (differs from the generic PROTEUS description above —
  treat this file, not `proteus_CLAUDE.md`, as the source of truth for which
  modules this project actually uses):
  - `interior_struct.module = "zalmoxis"`
  - `interior_energetics.module = "boundary"` (a parametrised boundary-layer
    model, not `SPIDER`/`ARAGOG`)
  - `outgas.module = "atmodeller"` (not `CALLIOPE`). Note the fiducial config
    does not set any `outgas.atmodeller.eos_*` fields, so they sit at their
    schema default (`None` = ideal gas) — real-gas non-ideality in the
    outgassing/solubility equilibrium is *not* currently enabled, only in
    AGNI's atmosphere structure (`atmos_clim.agni.real_gas = true`, a
    separate, unrelated switch — see the `proteus-config-review` skill).
    Also note some exploratory sweep folders in PROTEUS `output/` use a
    `calliope`-suffixed variant instead; check which outgassing backend a
    given sweep used before comparing it against others.
  - `atmos_clim.module = "agni"` (backed by `SOCRATES`, `spectral_group =
    "Dayspring"`, 48 bands)
  - `escape.module = "zephyrus"`
  - `observe.module = "petitRADTRANS"` — this is what generates each run's
    synthetic transmission spectrum.
  - `atmos_chem.module = "vulcan"`, run `when = "offline"` — still part of
    the automated PROTEUS pipeline, just executed as an offline post-step
    rather than inline each timestep.
  - `star.module = "mors"` (stellar evolution included, not blackbody).
- **Fixed K2-18 b system parameters**: `planet.mass_tot = 8.63 M_Earth`
  (Cloutier 2019), `star.mass = 0.495 M_sun` (Cloutier 2019),
  `star.mors.rot_period = 39.3 d` / `age_now = 3.0 Gyr` (Sairam 2025),
  `orbit.semimajoraxis = 0.15910 au` (comment cites Benneke 2019; not fully
  confirmed against the primary source, lower-confidence than the other
  citations here). Host spectrum is
  MUSCLES GJ 849 used as an M-dwarf substitute for K2-18. Note there is no
  explicit Teff input: with `star.module = "mors"`, Teff is *derived* each
  step from the Spada evolutionary track as a function of stellar mass and
  the simulation's elapsed stellar age, not read from a config field — see
  the `proteus-config-review` skill.
- **Grid axes live under these keys** — the fO2/H/C/N/S sweep should override:
  - `outgas.fO2_shift_IW` (fiducial: `-3`)
  - `planet.elements.H_budget` with `H_mode = "ppmw"` (fiducial: `10000`
    ppmw, ~1% EMF)
  - `planet.elements.C_budget` (fiducial: `0.32`, ~100x solar metallicity)
  - `planet.elements.N_budget` (fiducial: `0.09`, ~100x solar metallicity)
  - `planet.elements.S_budget` (fiducial: `0.04`, ~100x solar metallicity)

**Before launching any grid/batch run, this file must be diffed against its
copy inside the live PROTEUS working directory** — the two can and have
drifted out of sync. See the `launch-grid-batch` skill for exactly why and
how.

Simulation output for a run lives under `output/<run>/` in a PROTEUS working
directory (gitignored there); the per-timestep history is in `hf_all`/`hf_row`
type records with periodic interior snapshots (`<iter>_int.nc`) under `data/`.
Atmospheric chemistry and the synthetic spectrum for each run are produced
automatically by the PROTEUS pipeline (no separate `observe`/`offchem` call
needed) and are written into that same per-run output subdirectory alongside
the physical output. See the `launch-grid-batch` skill for where a *sweep's*
output actually lands (`raw_grid_output/` vs. `PROTEUS/output/`), and the
`move-completed-sweep`/`harvest-batches` skills for getting it from there
into `simulation_data/`.

## Working conventions

- Keep `simulation_data/` as an input-only store for raw PROTEUS grid output;
  do all analysis/transformation in `plotting_scripts/`.
- `plotting_scripts/` scripts should be self-contained and re-runnable against
  `simulation_data/` to regenerate any figure in `paper/Figures/` without
  needing to rerun PROTEUS.
- Save each script's output figures into `paper/Figures/` (a subdirectory per
  script/topic is fine) so `main.tex` can `\includegraphics` them directly.
- Since this is destined for publication, favour clear axis labels with
  units, a colourblind-safe palette, legends, and vector formats (PDF) for
  figures, consistent with MNRAS figure conventions.
- Detailed, task-specific procedures live in `.claude/skills/` (see
  "Skills" above), not in this file — load the relevant skill when doing
  that task rather than expecting the detail to already be in context.
  When adding a new one-off procedure or debugging narrative worth keeping,
  prefer adding it to an existing skill (or a new one) over growing this
  file, unless it's project-wide orientation any conversation would need.
- **After staging a commit and pushing it to GitHub in this repo, always
  run the `backup-after-push` skill immediately afterward** (mirrors the
  project, including the large gitignored data directories, to the
  attached external hard drive — this is the only backup that data gets).
- Before editing the crontab for any reason, run `crontab -l` first and
  diff after — this machine's crontab has several independent scheduled
  jobs (see the `harvest-batches` and `cluster-tmp-cleanup` skills) and
  edits should only ever add/modify the one line intended.
